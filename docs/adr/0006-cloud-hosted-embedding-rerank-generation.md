# Cloud-hosted embedding, reranking, and generation via Voyage AI and Gemini

Supersedes ADR-0003's rationale for the reranker (ADR-0003 never covered embedding-model choice; its Guardrail/Llama Guard rationale is also untouched — that component isn't built yet). Supersedes ADR-0004 entirely.

The deploy target for this project doesn't run Ollama or have GPU/Metal-accelerated local inference available at all, so the local-first architecture ADR-0002/ADR-0003 established couldn't be deployed as-is. Separately, the Dev Generator's inability to reliably produce structured output had repeatedly capped eval quality — most visibly, Ragas' `faithfulness` metric computing for only ~34% of answered items in the hybrid+reranker baseline, and Abstention relying on a fragile plain-text marker string instead of a real structured signal.

Embedding (`bge-m3` via Ollama), reranking (self-hosted ONNX BGE-reranker-v2-m3), and generation (`llama3.1:8b` via Ollama) all move to cloud APIs: Voyage AI for embedding (`voyage-3`) and reranking (`rerank-2`), Gemini for generation and as the Ragas judge. Postgres/pgvector (ADR-0002) is unchanged — only the embedding/rerank/generation providers change, not the vector store or the hybrid dense+BM25+rerank+document-scoped retrieval architecture built on top of it.

This also retires the Dev/Validation Generator split ADR-0004 introduced. That split existed to avoid cloud cost during rapid iteration — a single local model answered every query during development and every Eval Gate run, with a cloud model (originally planned as Claude) reserved for one final run to produce reportable numbers. Two things changed that calculus: the deploy target has no local model to fall back to regardless, and cloud cost at this project's scale turned out to be negligible (low single-digit dollars for a full 200-question Golden Set run). There is now a single Generator, used identically in development, in every Eval Gate run, and in the final report.

## Consequences

- **Abstention moved to structured JSON output**, per ADR-0004's own stated forward plan for when a capable cloud generator — originally envisioned there as Claude, Gemini in practice — was wired in: the marker-string workaround was specific to the 8B local model's unreliable structured output, and is no longer needed now that a model capable of reliable structured output is wired in throughout.
- **The Ragas judge and the pipeline's own Generator/Embedder are the same models**, not a separate choice — this also resolved itself: an earlier decoupling (separate `JUDGE_LLM_MODEL`/`JUDGE_EMBED_MODEL` constants) was necessary only as an intermediate step while the judge was still on Ollama and the pipeline had already moved to Voyage AI/Gemini; once both sides matched, the decoupling was removed.
- **Dev/test now costs real money and is subject to real account rate limits**, unlike the previous free/local Dev Generator loop. In practice, the dev Voyage AI account's 3 RPM cap (no payment method on file) turned out to matter more than the per-call dollar cost — retry/backoff deviations from the default "no new fallback logic" stance were accepted case by case (embedding calls, then the Ragas judge's embedding calls) to keep the test suite and eval runs usable, documented on the relevant tickets rather than here, since they're operational workarounds for a specific account's tier, not architectural decisions.
- **No local fallback.** A Voyage AI or Gemini outage has nothing to fall back to and surfaces through the pipeline's existing generic error-handling path — an accepted consequence of retiring the local stack, not a resilience gap to fix.
- If cost or iteration speed becomes a real problem in practice, reintroducing a cheaper/faster tier for the dev loop specifically (not a full return to local inference) is a reasonable future decision — not assumed necessary by this ADR.
- **One residual, deliberate Ollama dependency remains**, unrelated to generation: the retrieval fusion step's `QueryFusionRetriever` (LlamaIndex) requires an `llm` constructor argument that this project's config (`num_queries=1`) guarantees is never actually invoked — a placeholder object is still constructed via `llama-index-llms-ollama`'s `Ollama` class purely to satisfy that constructor without it eagerly resolving a default OpenAI LLM instead. This isn't a naming or provider-choice question (the constant holding it, `_FUSION_LLM_PLACEHOLDER_MODEL`, was already provider-neutral before this ADR), and removing it entirely would mean writing a throwaway no-op LLM class for no behavioral benefit, so it was left as-is.
